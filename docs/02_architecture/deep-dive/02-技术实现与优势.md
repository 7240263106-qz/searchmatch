# 02 · 技术实现与优势

[返回总览与证据表](README.md) · [运行调用链](01-运行流程与调用链.md) · [优化方案](03-问题痛点与优化方案.md) · [答辩表达](04-项目包装与答辩表达.md)

以下痛点是从业务材料和当前机制做出的设计分析，不代表已有用户访谈、事故记录或量化收益。评价依据是机制是否解决具体矛盾，以及能否解释失败边界。

## 1. 先确定项目真正要优化的对象

学生需要知道“我能否参加、何时截止、去哪报名”；管理人员需要知道“这些字段来自哪里、是否适用本届赛事、能否放心发布”。只把网页内容变成一段摘要，无法同时满足这两种需求。

因此应把项目的技术主线理解为：**来源材料 → 有适用范围的字段候选 → 人工采用的事实 → 面向查询的竞赛数据。**

这决定了最有价值的能力排序：事实语义和证据优先，其次是发现与抽取，再其次是发布一致性和工程配置。页面数量、数据库表数量及框架种类只能描述规模，不能代替技术优势。

## 2. 优势一：规则与模型分工，把 AI 放在可核对的流程中

**痛点：** 全靠规则难以覆盖公告表述变化，全靠模型又可能漏行、改名、猜测缺失字段，模型超时还会使整个录入流程不可用。

**当前机制：** 普通通知先用规则抽取字段与依据，再由模型补充缺失项；规则已有明确值时通常保留。模型配置不完整、返回异常或无文本时，保留规则结果并记录原因。解析服务自身不可用时，文本/CSV 还有独立直读降级。[E03、E04]

这实际上有两个不同的降级层：

```text
格式解析失败：文本/CSV 可直读；复杂二进制明确报错
模型抽取失败：保留已完成的规则抽取，不清空结果
```

**优势在哪里：** 模型增强与基本可用性解耦。管理员能看到“哪些字段有值、哪些待确认、哪次模型未完成”，而不是只能接受一段黑盒答案。

**还不能怎样表述：** 不能称为严格事实验证系统。普通模型字段的 snippet 未做完整原文匹配，8000 字符截断也可能漏掉文末信息。所谓置信度是标注等级，不是经过校准的正确率。

**可展开的工程判断：** 对事实抽取，先决定不变量，再让模型处理表达差异。不变量应包括字段类型、引用位置、适用范围、冲突状态；Prompt 只是其中一层，不能代替程序校验。

## 3. 优势二：学校目录单独建模，避免“格式正确、业务含义错误”

**痛点：** 学校认定目录通常是一份多页名单。同一行可能换行，一项内又有多个子赛。通用单场通知抽取器可能把整个目录当一场赛事，或者把 A 类误写为国家级。

**当前机制：** 目录解析按序号恢复完整名称，保留跨行和同序号子赛；识别学校 A/B/C 认定，将其存入专用字段。模型按小批次核验，必须与原文行数、序号、去空白名称和认定等级对应；出现不一致时保留原始规则行。[E04、E05、E08]

本地测试样本是三页 71 行目录，适合说明“有真实复杂输入及专项测试”，不能把它说成生产样本总量或模型准确率。

**优势在哪里：** 系统把“是什么”与“这所学校如何认定”分开，从数据语义上避免错误传播。目录只载明名称与学校认定时，报名时间仍保持缺失，这比生成一份看似完整的信息更有业务价值。

**设计边界：** 目录识别仍依赖特定文本布局，行内序号/名称/等级混排、扫描件和表格提取变化可能识别不到。它是有明确场景的解析能力，不是任意学校文档通吃。

**值得思考的取舍：** 目录模型目前主要是验证规则结果，不参与采用新结果。如果输入布局长期稳定且逐行核验几乎不产生新增价值，应优先测量其成本，再决定是否改为只对可疑行调用模型。

## 4. 优势三：受约束的官网发现，比“给模型一个浏览器”更容易解释

**痛点：** 搜索结果同时包含往届、转载、校内通知和官网首页；动态站点又需要 JavaScript。无限跟随链接容易耗时、访问无关站点或误把局部信息当全国信息。

**当前机制：** 多搜索源提供候选，程序维护已访问集合、候选分数、年份和范围；模型仅选择候选编号及是否翻页，程序验证输出，再按不同主机最多 4 个并行访问。获得足够证据、候选耗尽、达到总时限或长时间无进展时停止；模型失败后规则继续。[E06]

动态页面使用受限浏览器补充：程序列出可导航控件、过滤危险或提交类控件，并限制 GET、资源数量、字节数、浏览器并发和会话时长。发现链路的网络读取还包含逐跳地址检查及固定已验证 IP 的连接方式。[E07]

**优势在哪里：** 模型负责判断“下一步值得看什么”，系统保留“允许看什么、允许执行什么、哪些内容能成为事实”的控制权。这个分工可以支撑 AI 应用工程的深入追问。

**设计边界：** HTML 搜索依赖外部页面结构；部分赛事有专用解析和可配置固定线索；任务记录在内存里。普通信息源采集并未完全共用同样的网络策略，不宜把最强路径的保障扩大到所有路径。

**适合的技术命名：** 可以说“模型辅助的受约束网页采集”或“有边界的采集 Agent”。没有多 Agent 协作、向量库和通用规划平台的证据。

## 5. 优势四：字段级证据与人工采用，使“为什么这样填”可以追查

**痛点：** 只有竞赛记录无法解释日期和报名入口从哪里来；重识别后直接覆盖又容易把人工修订或旧依据丢掉。

**当前机制：** 文档解析结果有版本和采用标记，确认时验证当前结果；入库保存来源、字段值、摘录、位置、提取方式、置信度与人工修订标记。官网保存只接收选择标识，实际字段从服务器保存的候选中恢复。[E03、E06、E08、E14]

**优势在哪里：** 可以从页面字段追到解析版本与材料位置，人工校正也有标记。对于管理平台，这比“模型生成过一个 JSON”更接近可维护的工作流程。

**设计边界：** 当前并非完整不可变证据图。部分同源字段更新会删除旧 FieldEvidence；CompetitionVersion 也不是每条路径都保存全部字段差异；更正后的值可能与原摘录不同，因此不能宣称所有历史值都可完整重建。

**下一步应该强化什么：** 引用的内容真实性、适用实体与范围，以及“候选证据—采用动作—当前值”的显式关联，比单纯增加一个文本来源字段更有意义。

## 6. 优势五：条件更新和事务，保护多个业务状态一起变化

**痛点：** 两个人同时采用不同结果，或者一人删除文档、另一人确认导入，可能形成覆盖、重复和失去材料依据的数据。

**当前机制：** 官网字段保存使用 versionNo 条件更新；提交审核、发布、驳回等主路径也结合状态与版本。事务同时写业务记录、审核/版本记录和 Outbox 事件。文档确认在事务里重新检查可用状态和采用版本。[E08]

删除文档采用可重试的两段流程：先保留 deleting 状态并检查没有运行中任务，删除原件，再事务清理解析记录和关联；保留已有竞赛，并处理来源/依据引用。失败保留删除状态，阻止下载、重解析与陈旧确认，让重试有可识别的起点。[E02]

**优势在哪里：** 项目已经处理“异步处理与人工操作交叉”的真实一致性问题；这比单个 CRUD 接口更能说明工程深度。

**设计边界：** 不是所有入口统一使用同一策略；审计通常在业务事务之外，普通抓取多步写入也不全在一个事务里。Outbox 只有持久化写入，尚未查到完整投递消费者。因此适合表述为“关键写路径的事务与并发校验”，不应声称系统已经达到端到端恰好一次。

## 7. 优势六：保存值与运行值分离，配置页面能说明系统实际状态

**痛点：** 配置显示“保存成功”不代表运行进程已切换；多人修改可能互相覆盖，凭据也不应直接进入普通配置返回值和审计。

**当前机制：** 配置项有定义、分组、类型、校验及生效方式。保存基于 baseVersion 和数据库版本快照，冲突时返回版本信息；新版本以事务保存。待重启项保留旧运行值并显示 pending_restart，初始化时处理重启生效；历史版本支持 diff 和回退。模型凭据通过本地 AES-256-GCM 加密库保存，业务持有引用。[E10、E11]

**优势在哪里：** 从“表单改参数”提升到“有版本、有生效状态、有运行来源的配置管理”。这适合作为后台工程的第四条主亮点，尤其可以解释为什么需要 saved/runtime 两套值。

**设计边界：** 当前配置解析器和凭据缓存服务于单进程，不能称为分布式配置中心。数据库版本保存、应用状态写入、审计与回退是多步骤，极端并发/失败仍需核验；即时探针也不是所有远端配置都进行了真实连接测试。

## 8. 时间与质量规则，是应归入主线的细节

### 时间不能只有一个 Date

项目用 `at + precision + timezone + rawText` 保存时间。只写“2026 年 11 月 17 日截止”时，以业务时区当日日末计算，避免在零点误认为截止；无法确认的相对时间保持未知。多赛道摘要还会选取下一阶段并保留赛道差异。[E09]

其价值是维护原文语义，并不意味着所有边界都完善。当前未来开始且 7 天内截止的阶段会先命中 closing_soon；非法日历日期也可能被 Date.UTC 自动滚动。两个边界应在修正后补回归，详见优化方案和局部探针。

### 可信度不是概率

质量计算把来源、完整性、多来源与人工审核拆成可解释分项；纯占位文字不视为补齐，冲突优先，并限制冲突场景的最高可信度。[E09]

这能解释“为什么是中可信”，但不能说“90 分等于 90% 正确”。独立来源计数在部分调用中还是固定值，域名不同也不天然代表独立来源。质量规则应服务人工判断，而非替代事实核验。

## 9. 技术选择怎样讲才有说服力

| 选择 | 当前规模下的合理性 | 代价与触发演进的条件 |
| --- | --- | --- |
| NestJS + Prisma + SQLite | 一个管理工作区、部署链路短；关系模型、事务和唯一约束可用 | 写并发、锁等待或多个 worker 成为实测问题后，再评估 PostgreSQL；迁移还涉及 DDL、JSON 查询、索引和恢复演练 |
| Python 独立解析器 | 复用成熟文档库，让文件格式处理与业务 API 分开 | Base64 放大内存与传输；大文件或并发解析增多后需要文件流、对象引用和进程资源隔离 |
| TypeScript 共享 contracts | 减少前后端枚举与响应字段定义漂移 | 编译期约定不能替代接口运行时校验，Python 侧也要有版本化协议 |
| HTTP 优先、浏览器补充 | 静态资料无需启动浏览器，动态场景有补充通道 | 浏览器成本高，应以动态页命中率、资源使用和超时比例决定池化策略 |
| 规则 + 模型 + 人工 | 规则保证基础输出，模型处理表达差异，人工承担事实采用 | 三方输出口径要统一，冲突与依据不应在合并时丢失 |
| 单体内服务划分 | 当前部署和排查相对直接 | 先稳定模块边界与任务恢复，再决定独立 worker；不需要因存在多个 Service 就拆微服务 |

## 10. 最值得讲的四条支柱

正式项目介绍建议收敛为：**异构资料与字段证据、受约束官网发现、事务与版本控制、配置版本及运行状态。** 时间语义、目录专项、删除一致性都放在所属支柱中展开，避免把简历写成十几个零散功能。

如果偏 AI 应用岗位，先展开“模型选择—程序验证—规则降级”；偏全栈/后端岗位，先展开“候选—采用—事务写入—查询”的状态和契约。技术事实保持一致，只调整讲述重点。
