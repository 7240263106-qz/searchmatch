## 1. 项目定位：把分散竞赛资料整理成能核对的事实

推荐项目名称：**方湖观澜 · 竞赛信息采集与证据核对平台**。

如果用于竞赛答辩，可沿用既有“学科竞赛信息智能感知平台”名称，并在副标题里说明“目录解析、官网发现、字段核对与审核发布”。名字可以概括愿景，答辩中仍按已实现能力展开。

一句话定位：**面向高校学生与竞赛管理人员，汇集学校目录、赛事通知和官网资料，提供带字段依据的竞赛录入、核对、发布与检索。**

岗位侧重可以有两种：

| 方向 | 先讲什么 | 需要掌握的源码 |
| --- | --- | --- |
| 全栈 / TypeScript 后端 | 从文档录入到版本校验、事务发布、条件查询的完整链路 | E01—E05、E08—E10、E12、E15 |
| AI 应用工程 | 规则与模型协作、候选约束、引用证据、模型降级和受限浏览器 | E03—E07、E11 |

进取定位可写“竞赛资料采集工作流与质量治理”，但要能讲清当前执行仍依赖进程内任务。可靠工作流引擎、统一模型预算、全量可查询读模型属于后续增强，不能作为当前完成项。

## 2. 可用于项目介绍的简介与四条亮点

**项目简介：** 面向高校竞赛资料分散、学校认定与赛事通知口径不同的问题，构建基于 React、NestJS 与 Python 解析服务的信息平台，支持文档录入、当年官网资料发现、字段依据核对及竞赛发布检索。

- **异构文档与字段证据：** 将 PDF 文字层、DOCX、XLSX 和文本材料转换为带位置的文本块，先用规则抽取竞赛字段，再由模型补充缺失信息；对学校认定目录逐行还原名称与 A/B/C 等级并分批核验，模型失败保留规则结果，确认入库时保存字段依据和解析版本。
- **受约束的官网发现：** 汇集多搜索源和已核验线索，按赛事身份、年份与范围筛选候选；模型只从候选编号中选择访问或翻页，程序约束并发、访问时限和网络读取，动态页面用受限浏览器补充，采集结果由用户按来源选择后保存。
- **关键写入的事务与版本校验：** 官网字段采用和主审核路径使用条件更新检查版本与状态，在数据库事务中关联业务记录、版本或审核记录及事件；文档删除保留可重试状态，阻止运行中解析与陈旧确认交叉写入。
- **配置版本与运行状态：** 按配置定义校验类型、取值和跨项约束，基于版本快照识别并发修改；区分保存值、运行值和待重启状态，提供版本对比与回退，模型凭据加密保存并通过引用供服务使用。

这四条突出的是当前系统能力。用于个人简历时，应只选自己实际参与并能讲透的部分，再据实加入“实现/参与/负责模块”等动词；源码存在某项能力并不证明个人负责该项。

## 3. 两分钟项目讲解

> 这个项目面向高校竞赛信息收集。学生关心能不能参加、什么时候截止、在哪里报名，管理人员还需要核对这些信息的来源。难点是这些信息分散在学校目录、赛事官网、通知和附件里，而且口径不一样，例如学校 A 类认定不等于国家级，学校选拔截止也不等于全国报名截止。
>
> 系统主要有两条录入链路。文档链路先用 Python 提取文字和所在页、段落或表格行，再区分普通通知和多竞赛目录。普通通知采用规则先提取、模型补充的方式，模型不可用时保留规则结果。目录则按序号恢复完整名称和学校认定等级，模型分批返回后要与原文逐项对照，不能随意增加报名时间等信息。
>
> 官网发现链路会结合搜索结果和已核验线索，筛选本届赛事的官网和公告。模型可以判断下一步访问哪个候选或是否翻页，但实际地址、并发、年份范围和网络安全由程序控制。动态页面有受限浏览器补充，最后仍由用户核对并选择字段。
>
> 入库时保存字段依据与版本。官网采用和主审核路径通过版本条件与事务减少并发覆盖，配置模块还区分保存值和运行值，能显示待重启状态。当前最值得继续优化的是统一所有写入口的授权与状态校验、补齐后台任务恢复，以及把检索过滤和分页下推到完整读模型。这些是下一阶段计划，当前没有把它们写成已完成能力。

## 4. 按“痛点—方案—价值”展开的答辩要点

| 痛点 | 当前实现 | 可以讲的具体价值 | 不能扩大的结论 |
| --- | --- | --- | --- |
| 材料格式和布局不同 | 独立 Python 解析器、文本块与位置、目录专项 | 统一供字段抽取使用，目录不被误当一场赛事 | 任意格式、扫描件 OCR 已全支持 |
| 模型可能失败或补猜 | 规则先行、JSON 解析、目录严格对照、失败降级 | 模型不可用仍可核对规则结果 | 所有模型字段都已事实验证、零幻觉 |
| 搜索混入往届与校内通知 | 年份/身份/范围规则、受约束候选调度 | 把“官网候选”和“可录入通知”区别处理 | 覆盖全网、所有赛事零维护 |
| 人工采用会碰到并发修改 | 关键路径 expectedVersion 与状态条件、事务 | 旧结果不能静默覆盖新版本 | 所有入口都已有统一并发协议 |
| 删除原件与后台解析交叉 | deleting 状态、运行中任务检查、两段清理 | 中间失败能保留重试状态 | 文件与数据库跨存储原子提交 |
| 配置保存不等于生效 | saved/runtime、pending_restart、版本回退 | 管理员可以判断运行状态和生效边界 | 多实例强一致配置中心、回退必定成功 |

## 5. 面试主问与递进回答

### Q1：这个项目的技术难点为什么不只是爬虫和增删改查？

触发：项目简介、全部亮点。阅读：[调用链第 3—6 节](01-运行流程与调用链.md)、[优势第 1—5 节](02-技术实现与优势.md)。

**回答：** 难点在把不同来源整理成同一套可采用事实。相同的“截止时间”可能属于学校选拔、地区赛道或全国赛事；目录的 A/B/C 也只是学校认定。因此系统需要在抽取前确认来源身份与适用范围，在抽取后保留字段依据、缺失与冲突，再让人采用。数据库写入和页面展示只是这条流程的后半段。

**追问：最容易错的一个例子？** 把文章发布日期当赛事年份，再把校内组织参赛的截止当全国截止。当前官网发现会先检查年份和校内范围，目录认定也与赛事 level 分字段。普通文档路径仍需加强范围和引用验证，这是设计边界。

### Q2：为什么规则和模型一起用？冲突时听谁的？

触发：异构文档与字段证据。阅读：[调用链 3.4](01-运行流程与调用链.md)、[优势 2—3](02-技术实现与优势.md)。

**回答：** 规则适合识别明确锚点和固定目录结构，能稳定保留原文位置；模型适合补充不同表述里的缺失字段。当前普通合并通常保留规则已有明确值，模型失败也不丢弃规则结果；发现多个日期的规则路径会保留冲突候选。学校目录更严格，模型必须与原行一致才算核验完成。

**追问：规则提错了会怎样？** “优先规则”不保证正确。人工核对仍然必要，后续应把规则与模型结果都作为有依据的候选，按原文支持度与适用范围决定采用。不能靠覆盖顺序代替事实判断。

**追问：Prompt 写了不能猜，还需要程序校验吗？** 需要。Prompt 约束生成意图，schema 约束结构，原文定位与字段规范化约束事实；三者作用不同。当前普通模型 snippet 尚未严格验证，我不会把它讲成已经完成引用级事实校验。

### Q3：这个官网采集 Agent 的“智能”具体体现在哪里？

触发：受约束官网发现。阅读：[调用链第 4 节](01-运行流程与调用链.md)、[优势第 4 节](02-技术实现与优势.md)。

**回答：** 模型结合已取得的字段、访问结果和剩余候选，判断下一步访问哪一页、是否翻页或结束。它只输出现有候选编号。程序检查编号、每主机动作和波次并发，再通过受保护网络读取，核验年份和范围后抽取。模型失效时切回规则，所以智能判断和执行边界是分开的。

**追问：为什么不让模型生成 URL？** 候选来自真实搜索或页面链接，限制编号可以避免编造地址，也便于统一网络检查和复现决策。动态浏览器同样只暴露经过筛选的导航控件。

**追问：如果模型一直翻页呢？** 当前有已访问集合、同源分页检查、4 分钟总时限检查和 90 秒无进展停止；但不是统一取消信号驱动的硬预算。后续应把剩余时间传到每次 I/O，而不是只在循环边界判断。

### Q4：字段证据怎么保存？它能证明模型一定正确吗？

触发：字段证据。阅读：[优势第 5 节](02-技术实现与优势.md)、[优化第 3 节](03-问题痛点与优化方案.md)。

**回答：** 字段依据记录来源、片段、位置、抽取方式、置信度、人工修订标记和解析版本；用户可以从字段追到材料。它提供可核对性，不自动等于正确性。引用可能并不支持该值，也可能属于其他年份或赛道，所以还要验证引用、适用范围和规范化结果。

**追问：人工更正值和摘录不一样怎么办？** 保存更正标记与理由，把“原始证据候选”和“采用动作”分开。当前已有更正标记，但完整不可变证据历史与采用记录是后续要补齐的能力。

### Q5：两个人同时保存，怎么避免覆盖？

触发：关键写入事务与版本校验。阅读：[调用链 4.4、第 6 节](01-运行流程与调用链.md)、[优势第 6 节](02-技术实现与优势.md)。

**回答：** 以官网字段采用为例，服务器采集时保留竞赛版本，保存时用 id、versionNo 和可访问范围做条件 updateMany，成功才递增版本并写后续数据。两个保存请求基于同一版本时，只有一个能满足条件，另一个返回状态冲突，事务会撤销本次其他写入。主审核路径也按状态与版本做类似保护。

**追问：这和先查再 update 有什么不同？** 单纯先查不能阻止查询后发生其他更新。条件必须进入实际写 SQL，并用影响行数判断是否仍满足前提。

**追问：所有写入口都一样吗？** 目前没有。对话动作存在直接更新和入口角色差异，所以优化重点是统一命令服务，而不是仅给某个页面补一层按钮禁用。

### Q6：为什么写 Outbox？现在消息真的会发出去吗？

触发：事务中的事件。阅读：[优化第 4—5 节](03-问题痛点与优化方案.md)。

**回答：** Outbox 与业务事务一起提交，可以保留“业务变化已经发生，需要后续处理”的事件意图。当前源码有事件创建，没有查到完整的投递消费者，所以它还不能证明订阅消息已经发出。

**追问：要完善怎么做？** 后台任务按租约领取 pending 事件、失败有限重试、成功标记；消费者按 eventId 幂等。发送成功但确认丢失时可能重投，所以通常按至少一次投递设计，不能声称天然恰好一次。

**追问：解析任务不是也有表，为什么还会丢？** 表里保留任务状态不等于有执行恢复。现在是进程内 Promise 执行，缺少租约到期接管与检查点恢复。状态持久化和执行可靠性要分别说明。

### Q7：配置版本为什么还要保存运行值？

触发：配置版本与运行状态。阅读：[调用链第 7 节](01-运行流程与调用链.md)、[优势第 7 节](02-技术实现与优势.md)。

**回答：** 某些配置保存后可以立即生效，监听地址等启动参数则需要重启。只有一份值，页面容易把新保存值误认为进程正在用的值。当前保存值和运行值分离，待重启期间业务读取旧运行值，界面显示 pending_restart；配置更新还有版本校验，防止用户基于旧表单覆盖新修改。

**追问：回退是否总成功？** 不是。回退也是写入和应用过程，当前失败会记录日志，仍需展示真实结果。下一步要加入可恢复应用状态，并防止失败版本的自动回退覆盖后来管理员提交的新版本。

### Q8：你优先优化哪里？为什么不先加缓存或搜索引擎？

触发：项目整体设计。阅读：[优化第 1、6、9 节](03-问题痛点与优化方案.md)。

**回答：** 先统一写入权限和状态，再处理引用与时间正确性，然后补任务恢复。检索当前先取最多 500 条再过滤排序，存在查不全的问题，应该先建立可完整筛选的阶段/赛道读模型并在数据库分页。缓存不能修正截断，搜索引擎也不应成为掩盖领域语义不一致的方法。

**追问：何时需要 PostgreSQL？** 当明确有多 worker 写并发、锁等待、复杂查询或数据规模瓶颈，并且测量证明 SQLite 已成为限制时。迁移要准备 schema、索引、JSON 查询、数据核对和回滚，不应只改连接字符串。
